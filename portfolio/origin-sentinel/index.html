Origin Sentinel: detecting dead services behind a healthy Cloudflare edge

Cloudflare Tunnel carries outside traffic to services on a private network. Its edge (Cloudflare's servers facing the internet) can report healthy while the service behind it is broken. I built an autonomous sentinel that checks the origin (the service itself) directly and classifies what is wrong. The first version only reports; write access is planned for a later phase.

How a healthy tunnel can hide a failed service

Edge and tunnel status answer one question: is the tunnel connected? They do not say whether the service behind the tunnel is alive.

Here is how that goes wrong. A container reboots, and DHCP (the service that hands out network addresses) gives it a new LAN IP, its address on the local network. The tunnel ingress (the rule mapping a public hostname to an internal address) still points at the old address. The edge then serves errors, or a different service, while every dashboard stays green. Monitoring that checks only the edge and the tunnel does not see this, because the failure sits between the tunnel and the service.

How the sentinel classifies origin state

The sentinel probes each origin from the local network side, bypassing Access (Cloudflare's login gate in front of the services), and classifies the state before it changes anything. It proposes a repoint, changing the ingress rule to the container’s new address, only when a container’s IP has changed.

Everything it finds is written to a machine-readable health.json file, so the next automated agent, or a person, starts from the recorded findings instead of diagnosing the problem again from scratch.

OK

DEAD_ORIGIN        # not running anywhere
TUNNEL_DOWN        # tunnel not connected
APP_UNHEALTHY      # running, answering with an error
NEEDS_HUMAN        # ambiguous; it will not guess

Safeguards on automatic repair

Automatic repair that can rewrite production ingress could take services down if it acted wrongly, so most of the engineering limits what the sentinel may do. In the report-only version these apply:

  • It writes proposed repoints into health.json and makes no Cloudflare changes.
  • Its Cloudflare API token has read permission only, so it cannot change the configuration.
  • A failure on one origin does not stop the checks on the others.
  • Heal-state writes are atomic: a write either completes or leaves the old file in place.

The repair logic that will apply repoints once write access is granted has its own limits:

  • Localhost origins (services addressed as running on the same machine as the tunnel) are excluded from automatic repointing.
  • A repair counts as confirmed only when the service returns a 2xx HTTP status (a success response).
  • A repoint preserves every existing config key and handles hostnames that have several ingress rules.

The decision logic is a pure functional core: it takes data, returns data and does no I/O (no network or file access). All side effects sit in a thin outer layer, and 63 tests cover the core.
