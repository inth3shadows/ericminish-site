Origin Sentinel: detecting dead services behind a healthy Cloudflare edge

Cloudflare Tunnel carries outside traffic to services on a private network. Its edge (Cloudflare's servers facing the internet) can report healthy while the service behind it is broken. I built an autonomous sentinel that checks the origin (the service itself) directly. It ships without write access until it has built trust.

What it is — autonomous origin-health detection, classification, and staged self-heal for Cloudflare-tunnelled services.

Status — built and reviewed, 63 tests passing, staged for a report-only production rollout.

Failure mode: a healthy edge in front of a dead service

Edge and tunnel status answer one question: is the tunnel connected? They do not say whether the service behind the tunnel is alive.

A container reboots, DHCP hands it a new LAN IP, and the tunnel ingress (the rule mapping a public hostname to an internal address) still points at the old one. The edge then serves errors, or a different service, while every dashboard stays green. I call this the silent-origin-behind-healthy-edge class. Standard monitoring checks the edge and tunnel, which is not the layer where this failure happens.

How the sentinel classifies origin state

The sentinel probes each origin from the LAN side, bypassing Access (Cloudflare's login gate in front of the services), and classifies the state before it changes anything. It proposes a Cloudflare ingress repoint only when a container's IP has changed.

Everything it learns is written to a machine-readable health.json, so the next automated agent, or a human, starts from recorded ground truth instead of diagnosing again from scratch.

Safeguards on automatic repair

Automatic repair that can rewrite production ingress could take services down if it acts wrongly, so most of the engineering limits what the sentinel may do:

  • Report-only v1. It proposes repoints into health.json and makes no Cloudflare changes. Write access is planned for a later phase, once the report-only version has built trust.
  • Read-scoped token. The token it uses can only read, so it cannot change anything.
  • Limits on damage from a wrong action. Localhost origins are excluded from automatic repointing; heal confirmation requires a stricter 2xx HTTP status; a repoint preserves every existing config key and handles hostnames with several rules; one origin's failure does not abort the run; heal-state writes are atomic (a write either completes or leaves the old file).
  • Tested core. The decision logic is a pure functional core: it takes data, returns data and does no I/O (no network or file access). All side effects sit in a thin outer layer. 63 tests cover the core.
