Cutting agent token cost without losing a byte

An AI agent calls tools such as search, file listings and API requests (an API is the interface a service exposes to other programs), and the model reads every result, so tool output is a large part of the token bill. Tokens are the units a model is limited and billed by. terse is a drop-in proxy that sits in front of any MCP server (Model Context Protocol, the standard way agents connect to tools) and compresses its output so the original can always be rebuilt exactly. On nine GitHub API payloads it used 59% fewer tokens.

Status: running in my own agent stack today, wrapping a code-intelligence server (a tool server that answers questions about source code) on every call.

Why tool output costs so much

Search results, directory listings and API responses usually come back as JSON, and that JSON is repetitive: the same field names on every row, the same values over and over, and padding. A result stays in the conversation, and the model reads the conversation again on each later turn, so a large result is paid for on every turn while it remains in context.

Why summarizing and bigger context windows fall short

Summarizing or truncating the output is lossy: it can discard information that a correct answer depends on. A bigger context window raises the limit on how much the model can hold, but every token is still billed, so the repetition costs the same.

terse has one rule: the compressed output can always be turned back into the exact original. A round trip means compressing the data and then restoring it. If a payload would not restore perfectly, terse treats that as a failure and sends the original.

How it shrinks things

  • Table form. Field names that repeat on every record are written once as a table header, and each row becomes a list of values in header order.
  • Dictionary form. Values that repeat are written once in a legend (a lookup table) and replaced by short references to it.
  • Cross-call diffs. When a tool returns something similar to its previous result, terse can send only the difference, and does so only when it can prove the difference rebuilds the full result.
  • Field offload. A very large value can be replaced by a handle (a short reference) that fetches the exact value on demand, so only the handle takes up context until the value is needed.
terse gate
$ cat tool-output.json | terse gate -

round-trip lossless: PASS
cl100k tokens: 1810 -> 881 (51.3% saved)

terse leaves output that is already compact unchanged, because the saving would be tiny. A short primer, sent once per session instead of with every result, teaches the model to read the dense encoding directly, so your own code needs no decoding step. Token counts on this page use cl100k, a widely used tokenizer (the tool that splits text into the tokens that are counted).

Measured against TOON

To test the claim against something outside the project, the benchmark compares terse with TOON, a published token-oriented serialisation format with the same goal. Both run over the same nine GitHub API payloads (365,144 raw tokens), every row is verified lossless, and tokens are counted with the same tokenizer. The results describe these GitHub payloads only; the saving on other tools depends on the shape of their output.

Percentages are the reduction in tokens against the raw JSON, so a negative number means the encoding made the payload bigger. TOON grows on nested records because it adds a key-path (the chain of field names leading to a value) at every level of nesting. terse writes a repeated nested object once: the gh_pulls row holds sixty copies of the same repository object, and terse reduces them to one legend entry.

TOON wins one row, gh_labels (19.0% against 15.2% for terse). That payload is a flat table of short, uniform values, the case TOON was designed for. Across the nine payloads the saving ranges from 80.3% on workflow runs to 0.0% on a single repository object. The benchmark harness in the repository measures the saving on other tools.

Re-measured on 4 August 2026 against a pinned corpus (a fixed, saved set of payloads). One row changed: gh_issues went from 32.7% to 38.8% when the encoder learned to build one schema (a description of a record's fields) that covers records of different shapes, which moved the weighted total from 58.3% to 59.1%. Every other row is byte-identical to the previous measurement, and uv run scripts/bench/benchmark.py in the repository reproduces the table.

Failure handling and safeguards

  • If any compression step fails, terse forwards the original tool result unchanged.
  • A difference against an earlier result is sent only when it provably rebuilds the full result. Otherwise terse sends the full form.
  • The compression logic has no side effects, which makes it easy to test. Tracking of in-flight calls is capped, so a flaky server cannot make terse leak memory.

Who this is for

terse suits anyone running MCP servers, agent harnesses (the programs that run an agent's loop of model and tool calls) or other setups that repeatedly feed large tool outputs to a large language model (LLM).
