Cutting agent token cost without losing a byte

An AI agent calls tools (search, file listings, API requests) and the model reads every result, so tool output is a large part of the token bill. Tokens are the units a model is limited and billed by. terse is a drop-in proxy that compresses that output without losing anything: 59% fewer tokens on nine GitHub API payloads, and the original can always be rebuilt exactly.

What it is — a lossless compression proxy that sits in front of any MCP server (Model Context Protocol, the standard way agents connect to tools) and shrinks its output.

Status — running in my own agent stack today, wrapping a code-intelligence server on every call.

Why tool output costs so much

Every search result, directory listing and API response comes back as repetitive JSON: the same field names on every row, the same values over and over, and padding. The model re-reads all of it on every turn, so the cost repeats with every tool call, every turn and every session.

Why summarizing and bigger context windows fall short

  • Summarize or truncate — lossy. Data is gone, so the result cannot be trusted where correctness matters.
  • Buy a bigger context window — you still pay per token. A longer window raises the limit but does not make the bloat cheaper.

terse has one rule: the compressed output can always be turned back into the exact original. A round trip means compressing the data and then restoring it. If a payload would not restore perfectly, terse treats that as a failure and sends the original.

How it shrinks things

  • Table form — repeated field names collapse to a header; rows become positional.
  • Dictionary form — repeated values become short back-references to a legend.
  • Cross-call diffs — when a tool returns something similar to last time, terse sends only the difference, and only when it can prove the difference rebuilds the full result.
  • Field offload — a very large value is replaced by a handle (a short reference) that fetches the exact value on demand, so it takes no context until needed.
terse gate
$ cat tool-output.json | terse gate -

round-trip lossless: PASS
cl100k tokens: 1810 -> 881 (51.3% saved)

terse skips output that is already compact, because the saving would be tiny. A short primer, sent once per session instead of with every result, teaches the model to read the dense encoding directly, so your own code needs no decoding step. Token counts here use cl100k, a widely used tokenizer (the tool that splits text into the tokens that are counted).

Measured against TOON

To check the claim against something outside the project, the benchmark compares terse with TOON, a published token-oriented serialisation format with the same goal. Both run over the same nine GitHub API payloads (365,144 raw tokens), every row is verified lossless, and tokens are counted with the same tokenizer.

Percentages are the reduction in tokens against the raw JSON, so a negative number means the encoding made the payload bigger. TOON gets bigger on nested records because it adds a key-path at every level of nesting. terse collapses repeated subtrees: the gh_pulls row is sixty copies of the same repository object reduced to one legend entry.

TOON wins one row, gh_labels (19.0% against 15.2%), and the row is included. It is a flat table of short uniform values, the case TOON was designed for.

Re-measured on 4 August 2026 against a pinned corpus. One row moved and the total moved with it — gh_issues from 32.7% to 38.8%, the weighted total from 58.3% to 59.1%, when the encoder learned to build one schema across a union of record shapes. Every other row is byte-identical to the previous measurement, and uv run scripts/bench/benchmark.py in the repository reproduces the table.

Failure handling and safeguards

  • Fail-open. If any compression goes wrong, terse forwards the original result, so the tool call always completes.
  • Self-verifying. A diff is only sent when it provably reconstructs the result; the full form is always the fallback.
  • Bounded. The compression logic has no side effects, so it is easy to test. In-flight tracking is capped, so a flaky server cannot leak memory.

To the caller, the only visible change is lower token usage.

Who this is for

terse suits anyone running MCP servers, agent harnesses or other setups that feed large tool outputs to an LLM repeatedly. On the benchmark it cut tokens by 59.1% with an exact round trip.
