My semantic search worked at 1,000 documents and failed at 57,000

I built a hybrid retrieval engine (keyword search combined with embedding-based search) over years of my own working notes and measured it. The measurement showed that half of it does not work. This page describes that result.

What it is — keyword search and embeddings (numeric representations of text meaning) fused, then re-ranked (a second model reorders the top results). Runs entirely offline, on CPU.

Status — private repository.

Development corpus versus full scale

On a 1,271-chunk development corpus the semantic arm beat keyword search on paraphrased questions, where you describe a memory in different words than you originally used. That justified building a hybrid.

Measured at full scale for the first time, against ten questions judged by hand, it returned something useful five times. Every success was a keyword-shaped question. Four of the five paraphrased questions, the case the semantic arm was built for, returned nothing useful.

The correct answers were being retrieved, and the semantic arm ranked them too low. Keyword search alone (BM25, a standard keyword-ranking formula) beat every hybrid configuration, the reverse of the small-corpus result. Similarity scores stop separating good matches from bad as the pool of candidates grows.

How the investigation went

  1. Small corpus. 1,271 chunks. Semantic beat keyword on paraphrase.
  2. Full scale, five of ten. Judged by hand, no partial credit.
  3. First hypothesis tested. The hypothesis was that the bigger corpus was diluted. I tested it by restricting the search to the single highest-quality source. There was no improvement, so the hypothesis was rejected in one run.
  4. Recall versus rank. A diagnostic separated answers that were never retrieved (a recall problem) from answers that were retrieved and then ranked too low (a rank problem). The problem was rank.
  5. The shipped router made results worse. A query-adaptive router, which uses the expensive re-ranker only when the query looks keyword-shaped, had been tuned on the small corpus and shipped as the default. At full scale it scored worst of six configurations: 0.000 on paraphrased questions, where always re-ranking scored 0.200. It was removed as the default the same day.
  6. A bug in the scorer. A code review found the scorer retrieving deeper than the judging pool went, so the re-ranked configuration returned documents nobody had graded and was marked wrong for them. Fixing it raised that configuration from 0.352 to 0.447. The overall conclusion stayed the same.

Evaluation methods used

Pre-registered kill gateA stop condition written before anything was built: if a local re-ranker did not beat the existing baseline, the project would stop after one session.
Restraint in tuningA threshold that visibly underperformed was left alone instead of being re-tuned against eight unlabelled examples. This happened twice, and the plan file records the decision both times.
Negative controlsTwo questions with no answer anywhere in the corpus, used to check that the system does not invent matches. The semantic arm scored a nonsense query about sourdough hydration 95% as highly as an answerable question. Its confidence score carries almost no information.
Pooled, blind judgingCandidates were pooled from five retrieval configurations and shuffled, with no indication of which system found them. This stops the incumbent from winning by being graded only on its own results.
Judge reliabilityLabels are stamped with who produced them, and a separate tool samples them to compute inter-rater agreement (how often two judges give the same label) before they are trusted.
Answers in files the index already returnsFor several failed questions the answer was in a file the index returns for other questions. The corpus covered them, and the system failed to connect a paraphrased need to a document it already holds.
