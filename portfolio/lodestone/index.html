My embedding search beat keyword search on 1,271 chunks of notes and lost to it on the full collection of 57,500

I built a hybrid retrieval engine over years of my own working notes. It combines keyword search with embedding-based search, which compares numeric representations of what each passage means, and I measured how well it finds things. On a 1,271-chunk development set the embedding side beat keyword search. On the full collection of 57,500, keyword search alone beat every hybrid configuration I tried, and four of the five paraphrased questions returned nothing useful.

What it is — keyword search and embeddings fused into one result list, then re-ranked (a second model reorders the top results). It runs entirely offline, on CPU.

Results on the development set and on the full collection

The notes are split into chunks (short passages of text). On a development set of 1,271 chunks, I tested paraphrased questions, which describe a memory in different words from the ones I originally wrote. On the evaluation score, where higher is better, the embedding side scored 0.731 and keyword search scored 0.436. I then built the hybrid.

I then measured it on the full collection for the first time, with ten questions whose results were labelled by Claude (an AI model) with no partial credit and not yet checked by me. The hybrid engine returned something useful for five of the ten. All five successes were questions that share words with the notes they should find. Four of the five paraphrased questions, the case the embedding side was built for, returned nothing useful.

The embedding side was finding the correct answers but placing them too far down the list, at rank 107 and below rank 200 in two cases. On the full collection, keyword search alone beat every hybrid configuration, the reverse of the development-set result. In this evaluation, the embedding similarity scores did not separate good matches from bad ones once the collection was large.

For several of the failed questions, the answer was in a file the index returns for other questions. The collection held the answer, and the system did not connect a paraphrased question to a document it already had.

How the investigation went

  1. My first explanation was that the larger collection was diluted by lower-quality material. I tested it by restricting the search to the single highest-quality source of notes. Restricting the search to that source did not improve results in that run, so I rejected that explanation.
  2. A diagnostic then separated answers that were never retrieved (a recall problem) from answers that were retrieved and ranked too low (a ranking problem). The failures were ranking problems.
  3. A query-adaptive router, the component that decides for each question whether to run the expensive re-ranker, had been shipped as the default. It ran the re-ranker only when a question looked like a keyword search, and it had been tuned on the development set. At full scale it scored worst of six configurations: 0.000 on paraphrased questions, against 0.200 when the re-ranker always ran. I removed it as the default the same day.
  4. A code review found that the scorer retrieved deeper than the set of results that had been judged. The re-ranked configuration was returning documents nobody had graded and was marked wrong for them. Fixing the bug raised that configuration’s score from 0.352 to 0.447. The overall conclusion stayed the same.

Evaluation methods used

A stop condition written in advanceBefore anything was built, I wrote down that the project would stop after one session if a local re-ranker did not beat the existing baseline.
No tuning on unlabelled examplesA threshold that visibly underperformed was left alone instead of being re-tuned against eight unlabelled examples. This happened twice, and the plan file records the decision both times.
Questions that have no answerTwo negative controls, questions with no answer anywhere in the collection, check whether the system invents matches. The embedding side scored a nonsense query about sourdough hydration 95% as highly as an answerable question, so on this test its score barely separated an unanswerable question from an answerable one.
Judging pooled results without knowing their sourceCandidates were pooled from five retrieval configurations and shuffled, with no indication of which system found them. This stops the existing system from winning by being graded only on its own results.
Who produced each labelEach label records who produced it. All 194 labels so far came from Claude, and the agreement check against my own labels has not been run yet. A November 2026 re-test, which I judge myself, will replace them.
