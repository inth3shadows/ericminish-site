A benchmark built from bug-fix commits in my own code

A public benchmark reports how a model does on other people’s repositories, with each task run once. Neither fits a decision about which model to route my own work to, so this benchmark mines bug-fix commits from my own repositories and runs each task three times.

What it is — harvest, run, grade, report. A task is a commit from git history; a pass means that commit’s test suite goes green.

Status — private repository, in use for routing decisions across a local model gateway.

Why build it: whose code, and how many runs

Whose code. A SWE-bench score (SWE-bench is a public benchmark of bug fixes in open-source repositories) does not show how a model behaves in a specific Go, Python or TypeScript codebase with its own conventions. So the harvester walks this machine’s own git history for commits that touch both a test file and a source file and are small enough to work as a single-shot task. The model is measured on the code it will be asked to work on.

How many times. Public benchmarks run each task once and report a single pass or fail. A model that passes a task once and fails it twice more is not “80% reliable” in any useful sense when production gives it one shot. Every model-task pair runs three times here, and the report carries an agreement rate and a bootstrap confidence interval (a range of plausible values found by resampling the results), so a gap between two models can be judged as noise or as a difference from more than one sample.

The table uses fifteen tasks that a cheaper model had already failed, each run twice per tier. pass@1 is the share of runs that pass on the first attempt. Every pass was verified: the test had to fail before the patch and pass after it, with no writes to the test file. The small tier solves 10 of 15 tasks where the large tier solves 15 of 15, at $0.51 per solved task against $2.09, so choosing between them is a routing decision.

The dollar levels are inflated because a large system preamble is sent with every call, and it is sent with all three tiers equally. Use the ratios between tiers; the absolute dollar levels are inflated.

A broken task and the four published figures it corrected

One task failed for every tier: zero passes out of two in each of the three tiers, with no timeouts and no variance. Identical failure across three capability tiers points to a broken task, because a hard problem would separate a large model from a small one.

The cause was the harness. The graded test was asynchronous, the repository declared its async plugin as an optional extra, and the command the benchmark ran did not install extras, so the test could not run at all. The check that confirmed it cost no model calls: check out the commit that holds the correct fix and run the graded command against it. It scored zero, so no patch any model wrote could have passed.

Three tiers had been reported a full capability step lower than they were, because of a task nothing could pass. The task was repaired and re-run instead of dropped, and the findings file now shows each wrong figure inline next to the one that replaced it.

Three of the four corrections cost zero model calls: they were recomputations of data already on disk. The write-up had drifted from its own results because nothing regenerated it. That file is now generated from the graded runs.

Why scores cannot be compared across repositories

Because models are scored on my own code, a score from this project describes one model, one corpus, one revision and one date. It is not a leaderboard entry, and scores from different repositories cannot rank the models against each other.

Making scores comparable across corpora would mean abstracting away the codebase: its conventions, its test shapes and its commit habits. Those are what the benchmark measures.

The corpora differ before any model is called. Across a hundred repositories on two machines, the share of a repository’s history that qualifies as a task ranges from 4.0% to 74.5% among the thirty that yield any tasks. One repository measured 60.8% when its corpus was first built and 40.6% under identical criteria today. That is twenty points of drift from history growth alone, mostly automated release commits entering the total the share is calculated against.

  • Do not pool. One headline score over several repositories averages measurements that are not on the same scale.
  • Cite the revision and the date. Without them the number cannot be reproduced.
  • Re-harvest before comparing. Each run records its own qualification funnel (how many commits passed each filter), so a stale ratio is not compared against a fresh one by mistake.

What else it measures

  • Patch — coding ability, graded by running the model’s fix against a test suite.
  • Reading — effective context length (how much of its input the model can use), graded by exact retrieval of a fact planted in repository content.
  • Discovery — bug finding, graded by whether the reported line range overlaps the line range of the fix.
  • Scout — symbol-location accuracy, run through a tool loop (the model calls tools and reads the results over several turns) instead of a single chat completion, and graded against a deterministic symbol index.

Two failure modes are scored as failures and not retried. Determinism decays with output length, so identical prompts stop returning identical text past a few hundred tokens. And a reasoning model can return an empty response when its whole token budget went on reasoning it does not show. A retry would hide both.
