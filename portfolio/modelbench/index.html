A benchmark built from bug-fix commits in the repositories I work in

Public coding benchmarks such as SWE-bench, a set of bug fixes from open-source repositories, measure models on other people’s code and run each task once. I wanted to know which model to route my own work to. This benchmark turns bug-fix commits from the repositories on my machines into tasks and runs each task three times per model by default. It scores each model by what it costs per task it solves. In one comparison of fifteen tasks, the small tier solved 10 and the large tier solved 15, at $0.51 per solved task against $2.09.

What it is — a pipeline that harvests tasks, runs models on them, grades the results and writes a report. A task is a commit from git history, and a pass means that commit’s test suite goes green.

Status — private repository, in use for routing decisions across a local model gateway (a proxy that sends each request to one of several models).

Why it uses my own repositories and repeated runs

A SWE-bench score does not show how a model behaves in a specific Go, Python or TypeScript codebase with its own conventions. The harvester therefore walks the git history on this machine for commits that touch both a test file and a source file and are small enough to work as a single-shot task, one the model attempts in a single response. The model is measured on the code it will be asked to work on.

A single run per task gives one pass or fail, and a model that passes a task once and fails it the next two times looks the same in one run as a model that always passes. By default, every model-task pair here runs three times. The report includes an agreement rate and a bootstrap confidence interval (a range of plausible values found by resampling the results), so a gap between two models can be judged as noise or as a difference.

This comparison is smaller than the default protocol. It uses fifteen tasks that a cheaper model had already failed, and each task ran twice per tier, which gives 30 runs per tier. pass@1 is the share of runs that pass on the first attempt. Every pass was verified: the test had to fail before the patch and pass after it, with no writes to the test file.

The small tier solves 10 of 15 tasks and the large tier solves 15 of 15, at $0.51 per solved task against $2.09. On these tasks the large tier solved more and cost more per solve, so choosing between them is a routing decision.

The dollar amounts are higher than normal use would produce, because a large system preamble (fixed instructions sent before each task) goes with every call. It is the same for all three tiers, so compare the ratios between tiers in this experiment and treat the dollar amounts as inflated.

A broken task and the four published figures it corrected

One task failed for every tier: zero passes out of two in each of the three tiers, with no timeouts and no variance. A large model usually does better than a small one on a hard task, so an identical failure across all three tiers was a reason to check whether the task itself was broken.

The cause was the harness, the benchmark code that sets up and runs each task. The graded test was asynchronous, the repository listed the plugin needed to run asynchronous tests as an optional install, and the command the benchmark ran did not install extras, so the test could not run at all. The check that confirmed it cost no model calls: check out the commit that holds the correct fix and run the graded command against it. It scored zero, so no patch any model wrote could have passed.

All three tiers had been reported lower than they were, because each was charged a failure on a task that nothing could pass. The task was repaired and re-run instead of dropped, and the findings file now shows each wrong figure inline next to the one that replaced it.

Three of the four corrections cost zero model calls: they were recomputations of data already on disk. The write-up had drifted from its own results because nothing regenerated it. That file is now generated from the graded runs.

Why scores from different repositories should be kept apart

Because models are scored on my own code, a score from this project describes one model, one corpus, one revision and one date. A score from one repository and a score from another measure different sets of tasks, so ranking models across them needs that context.

Scores from different corpora reflect different conventions, test shapes and commit habits. Making them comparable would mean setting those differences aside, and they are what the benchmark is meant to measure.

The corpora differ before any model is called. Across a hundred repositories on two machines, thirty yield any tasks, and among those the share of a repository’s history that qualifies as a task ranges from 4.0% to 74.5%. The share also drifts. One repository measured 60.8% when its corpus was first built and 40.6% today under identical criteria, a twenty-point drop caused by history growth alone, mostly automated release commits that enlarged the total the share is calculated against.

  • One headline score over several repositories would average measurements that are not on the same scale, so scores are not pooled.
  • Each score is cited with its revision and date, without which it cannot be reproduced.
  • Repositories are re-harvested before a comparison. Each run records its own qualification funnel (how many commits passed each filter), so a stale ratio is not compared against a fresh one by mistake.

What else it measures

  • Patch mode tests coding ability by running the model’s fix against a test suite.
  • To measure effective context length (how much of its input the model can use), Reading mode plants a fact in repository content and requires the model to retrieve it exactly.
  • In Discovery mode the model looks for a bug, which counts as found when the reported line range overlaps the line range of the fix.
  • Scout checks how accurately the model locates a symbol (a function, class or variable). It runs as a tool loop, in which the model calls tools and reads the results over several turns. Its answers are checked against a deterministic symbol index, a lookup of where each symbol is defined that gives the same answer every time.

Two failure modes are scored as failures and not retried. The first is output that does not repeat: determinism decays with output length, so identical prompts stop returning identical text past a few hundred tokens. The second is an empty response from a reasoning model whose whole token budget went on reasoning it does not show. A retry would hide both.
