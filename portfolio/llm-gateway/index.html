One agent front-end, many model providers, one budget

A coding agent does not need a frontier model (the most capable and most expensive tier) for every call, because most of its work is mechanical. I built a personal gateway that routes a single agent front-end across a subscription frontier model and several cheaper open models. Secrets are keyless at rest (no API keys are stored in config files on disk), and a live display shows what the usage costs.

What it is — a multi-provider LLM gateway that lets one coding-agent front-end switch model/provider per task, with budget guardrails and spend history.

The problem with one model for everything

A subscription frontier model suits hard reasoning, but much of what an agent does, such as grepping a repo, summarizing a diff or running a mechanical refactor, does not need it. Paying frontier-model rates for that work wastes money, and choosing a cheaper model by hand for each task removes the benefit of having an agent. The gateway gives one front-end that routes each task to a suitable model.

The gateway

An OpenAI-compatible proxy (LiteLLM) sits in front of every provider I use: the subscription frontier model plus cheaper open models such as DeepSeek, GLM and Kimi. The agent talks to one endpoint whichever model answers.

A lightweight router lets me switch provider and model mid-session without restarting the agent. I also run an alternate agent harness (OpenCode) with a browser UI against the same pool, so routing works with more than one client.

router config
routes:
  default:      frontier/claude
  bulk-edit:    open/deepseek-chat
  summarize:    open/glm
  quick-search: open/kimi

# keys injected at runtime, never written here
providers:
  frontier: ${FRONTIER_KEY}
  open:     ${OPEN_KEY}

Cheap models handle the bulk, mechanical calls, and the frontier model is reserved for calls that need it.

How spend is tracked

Routing to cheaper models only helps if I can see whether it works. A status-line readout shows live spend against a per-key budget with color thresholds: green while there is headroom, amber near the limit, red over it. The figure appears on every prompt.

status line
[frontier: $3.40 / $10.00]  [open-pool: $0.85 / $25.00]

A small poller snapshots key spend into a Postgres table every few minutes, so the cost history can be queried over time and does not disappear when a dashboard refreshes. Whether routing saved money becomes a query.

How API keys are handled

  • Keyless at rest. The gateway and router configs hold no plaintext keys on disk.
  • Runtime injection. Keys are pulled from a secret broker (a separate service that stores them) at process start and are held only in memory.
  • Scrubbed on exit. When the process ends, the config is rewritten to its keyless stub, so config at rest never contains a key.

Config files can therefore be committed without leaking a key.
