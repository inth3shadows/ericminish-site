Measuring whether my coding agents improve, from what happened to their code

flight-recorder reads every coding-agent session saved on my machines and scores each one two ways: what it cost, and how much of the code it wrote was still in the repository later. It ignores the agent’s own report of success, because agents often report success on work that failed.

What it is: a Python tool that loads agent session transcripts and git history into SQLite and reports on them.

Cost and outcome are reported separately

Each session gets two sets of numbers, shown side by side. They are not combined into one score: a session can produce good code at a wasteful cost, and an average of the two would hide that.

To check whether a line survived, the tool hashes each line a session adds and looks for that line in the current version of the file. It matches on the line’s content, not on commit IDs, because rebasing or squashing changes every commit ID while the code stays the same.

It reads saved transcripts after the fact instead of running inside each session. That adds no delay to any session, loses nothing if a session crashes, and let it score 6,264 past sessions on the first day.

Four results the first version got wrong

  1. Tool error rate read 0.000 everywhere. Only about half of failed tool calls are flagged as errors. The rest come back as ordinary text starting with “Error” or “exit code”. The tool now checks for both.
  2. About 66% of sessions looked like failures. The first rework signal was “a later session edited the same file within 7 days”, which normal follow-up work also triggers. Rework is now measured from which lines survived, and the old signal is kept only as a secondary number over one day.
  3. One repository scored 0.448 survival; the true figure was 0.796. The rate was divided by every line recorded, including lines whose files the tool could not find. It now divides by lines it actually checked, and records an unchecked line as unknown rather than lost.
  4. One model looked much worse than another, 0.508 against 0.826. The weaker-looking model had mostly been used in one difficult repository. Models are now compared only on similar work: the same repository, the same task type and a similar change size.

Checks built into the reports

Intervals per sessionEach average has a bootstrap 95% interval computed over sessions rather than lines, since lines from one session are not independent. A difference whose interval includes zero is printed as inconclusive.
No averages from tiny samplesBelow a minimum number of sessions, the report prints the count instead of a value.
Credit by costA session is attributed to the command that accounts for most of its cost. Counting tagged messages instead had credited the most expensive sessions to a wrap-up command that runs at the end of every long session.
Missing is not zeroWhen a rate has no denominator it is stored as empty, so missing data cannot show up as a perfect score.
Call-level verificationA companion check confirms that each tool call in a transcript matches the call that was actually sent, and that each result matches the one delivered. It is used to check terse’s claim that its compression loses nothing.
Weaknesses listed up frontThe README lists seven known weaknesses. The largest: commits are linked to sessions by time, so a session that overlaps a manual commit gets credit for it.
