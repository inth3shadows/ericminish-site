An agent harness whose verdict on a code change comes from four checks and no language model

A language model writes the code, and a separate oracle (a program that reports pass or fail) decides whether the change is acceptable. That oracle is mechanical and deterministic, and no language model is part of it.

What it is — two halves: a model-free verdict on a code change, and the runtime that drives the loop producing those changes.

Status — private repository. The gate and the role runtime are built and in use; the self-driving loop is the work in progress.

How the verdict is decided

An agent that writes code is driven by a language model. Something else has to decide whether the change is acceptable. A common choice is a second model reviewing the first, but that reviewer can be confident about a bad diff, and it cannot be re-run to the same answer tomorrow.

So the language model has no part in the verdict. The verdict is four stateless checks (each keeps no memory between runs), and each one is a program that reports an exit code. Run it twice on the same tree and it gives the same answer, on any machine, with no network.

CheckFails when
teststhe project’s own suite does not pass
ir_contracta change leaves its declared scope, or removes a symbol without opting in
secretsa credential is found in the staged change
cvea reachable vulnerability is found (one the project’s code can trigger, as opposed to one that is only listed)

The symbol contract check uses the same deterministic index that powers RunEcho. A change declares the scope it intends to touch, and the gate compares the structural diff against that declaration. If an agent deletes a function while working on something else, a hash comparison catches it, and nobody has to notice it in review.

Passing the checks does not merge the change

When all four checks pass, the harness leaves the branch for a human to commit. There is no auto-commit. This is a deliberate guardrail.

“Autonomous” here means the plan, produce and verify cycle runs unattended, and a person still sees the result. The gate matters most when nobody is watching each step. In an interactive tool the human already judges every diff, so a mechanical oracle adds the least there.

Roles and the model gateway

The second half is the runtime. A role is a job — consult, scout, builder, reviewer, scribe — and a gateway resolves each role to whatever model currently does that job well. Swapping a model is a gateway configuration change and needs no code change here.

Roles carry tools, and the runtime runs the full request, tool call, result, request loop against them. There are two tool sets, a code-intelligence set and a retrieval set, and every tool in them is read-only. They can find, trace, fetch and reason. They cannot yet edit a file or run a command, and that is the remaining distance to a self-driving loop.

the four checks, illustrated
tests        the suite passes
ir_contract  scope held, no silent symbol removal
secrets      nothing credential-shaped is staged
cve          no reachable vulnerability

any failure  →  exit 1, nothing proceeds
all four     →  the branch waits for a human

The code-intelligence set picks its index by the question being asked. One index answers where a symbol is, live and always current. Another answers how things connect, stored and able to lag behind uncommitted edits. A structural answer costs a few hundred tokens where the file it was derived from costs thousands.

What runs the plan, produce and verify loop today

The orchestration that ties plan, produce and verify together does not yet run inside this project. It runs in a separate agent runtime, with each phase as an agent call. Today the harness supplies the judge and the tools, and that runtime supplies the loop.

One known gap: the harness’s own event records are currently written by asking a model to run a shell command. That conflicts with the project’s rule of keeping models out of the mechanical parts, on the write side. It is the first thing being fixed, before the event bus gets a read side and well before any write-capable tool set exists.

Runtime state is kept outside the repository: code lives here and state does not. Every step of a run is appended to a local event log as newline-delimited JSON (one JSON record per line).

Why the project is not an interactive coding tool

The alternative I considered and rejected was a model-agnostic interactive tool that a person drives. Matching an interactive coding assistant means matching its write tools, session loop, approval layer and context management, against teams orders of magnitude larger than one person.

The mechanical verdict has no equivalent in any of those tools, so the roadmap points at it.
