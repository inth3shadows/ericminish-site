Which user journeys could this change have broken?

Test-impact tools such as pytest-testmon and Ekstazi report which tests to run, and they need coverage data (a record of which code each test executed) from a previous run. testgraph reports which user journeys a change could break. It works from a static call graph, a map of which functions call which that is built without running anything, so it works on a repository that has never run its test suite.

What it is — a diff goes in, a short ranked list of user journeys comes out, each with a confidence.

Status — public, MIT, on PyPI. Standard library only, no third-party dependencies.

Why existing test-impact tools fall short

When an agent finishes a change it has to decide whether the change is done. Running the whole suite is safe but slow. Running nothing is fast but gives no evidence. Tools built for that gap (SeaLights, Datadog’s test impact analysis, pytest-testmon, Ekstazi) narrow the suite by recording which tests touched which lines on a previous run.

That recorded coverage is also their prerequisite. Coverage exists only after the tests have run, so none of these tools can say anything about a repository on its first day or about code nobody has exercised yet.

They also report in the wrong unit. A failing test_resolve_backfill says a test failed. It does not say that a claimant can no longer submit a signed form.

How it answers

  • A journey registry names each user-facing flow and the symbols it enters through — a route handler, a scheduler sweep, a CLI entry point.
  • Seeds — the changed line ranges in a diff are mapped to the symbols that own them. These symbols are the starting points of the search.
  • Reverse walk — the call graph is walked backwards, following callers of callers, to every symbol that depends on a seed.
  • Rank — the journeys whose entry symbols land in that set are reported, ordered by fan-in (the number of incoming connections).

testgraph[…]: 11 journey(s) this push could break,
d9174b7e1..0305ada6f, ranked:

  [ 23] J1   claimant submits a signed form
  [ 16] J10  staff regenerates and downloads the signed PDF
  …

Output from a git hook (a script git runs automatically, here before a push) on a private repository, name removed. The two figures are the fan-in rank and the journey’s identifier in that repository’s registry.

Confidence is the strongest path that reaches the journey: for each path take its weakest edge, then take the maximum across paths. A chain is as trustworthy as its worst link, and one solid route is enough. A journey reached only through weak or synthesized edges (links the analyzer inferred instead of reading a direct call) is labelled VERIFY MANUALLY and stays on the list.

Favouring recall over precision

The two kinds of error cost different amounts. Flagging a journey that turns out to be fine costs a few minutes. Dropping a journey that a change did break costs a production incident and the user’s trust in the tool. So testgraph is built for recall (finding every affected journey) and accepts over-selecting: edit a shared config file and it selects almost everything, because almost everything depends on it.

The same reasoning drives the integrity guard. Before answering, testgraph checks that the index (the stored call graph) is current and uncorrupted, and declines to answer from a stale or corrupted one. A wrong graph would produce a wrong “you don’t need to test that”, the one answer a test selector must avoid. Seeds come from line ranges, so an index built before the code moved would match the diff against line spans that no longer mean the same thing. If a changed file’s bytes still differ from the indexed copy after a re-sync, the answer is marked RECALL DEGRADED, meaning some affected journeys may be missing, and names the file.

Claims the evidence does not support

The usual pitch for test selection is suite reduction, and this page does not make it. In the regression-test-selection literature, static selection compares poorly with dynamic selection: the static tool STARTS reduced suites by 68.3% against Ekstazi’s 84.1% and had a 5.9% safety-violation rate (cases where a test that should have run was skipped). Dynamic beat static on both size and safety.

testgraph has selectivity numbers of its own across four repositories. They are not published here, because there is no measured missed-fault rate at those sizes to set beside them. Recall of 1.00 was measured on one target only: five hand-labelled commits and roughly twenty seeded mutation sites (small code changes injected to simulate bugs). A recall figure from one repository does not describe the tool in general.

The claim the evidence supports is that testgraph can answer on a cold start: no coverage, no CI, no prior runs. That is an advantage in positioning and could be copied, since an incumbent could collect coverage on the first build or add static analysis. It also has a cost: someone has to maintain the journey registry, which is hand-written judgement that nothing generates for you.

How it runs: git hook, ledger and MCP server

  • It runs on push. pre-push is the only git hook that receives a base commit to compare against: the remote’s sha (commit id) marks the boundary of what the remote does not have yet.
  • It does not block a push. Every path exits with code zero, including a blocked integrity guard, a missing index, a missing registry, a traceback and a timeout, so its output is advice only.
  • It records its own use. Every run appends a row to a local ledger, so how often the tool is called can be counted.
  • Agents can ask it directly. An MCP server (Model Context Protocol, the standard way agents call tools) exposes the ranked journeys as a tool. It uses only the standard library and imports lazily, and takes 15.2 MB of memory when idle against 62–69 MB for a typical SDK-based server. The difference applies to every editor window you have open.

The other half of the ledger records what running a journey then found. Joining the two halves on repository and commit gives the one figure the project has so far claimed without measuring: how often a journey failed on a commit whose selection did not name it.
