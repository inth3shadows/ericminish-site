About

I build infrastructure for AI agents and the data work that runs on it. I came to this work from operations. I live in Central Lake, Michigan.

I work on systems where it is unclear who owns a task, what state it is in, or whether it was finished, and I make those things clear.

My design rule

A system should decline to answer rather than guess. Following that rule has a cost each time, and these four projects show what it cost.

Lodestone, a search engineA retrieval engine I built beat keyword search on 1,271 documents and lost to it on 57,500. The write-up starts with the loss.
Frostline, a well-depth modelA modelling target scored 38.8% better than its baseline. Measured against the right baseline, it turned out to repeat a variable the model already had, so I dropped it.
terse, a compression proxyThe compression proxy in front of my agent’s tool servers sends the original, uncompressed output whenever it cannot prove the compressed version decodes back exactly. That is slower, but the agent never receives a damaged copy.
kb, an agent knowledge baseMy knowledge base accepts proposals from agents and reviews each one before saving it. Saving everything unreviewed was the cheaper option. I rejected it because past about 2,000 entries the important ones became hard to find.

Background

My professional work has been in operational systems: tracking the state of workflows, handling events, automating CRM processes, and building the reports that show afterwards what happened. I spend most of my time on the places where someone needs to know what happened, what happens next, and whether the record can be trusted.

AI agents have the same problem. An agent acts on information it cannot check directly, so most of my work on agents is deciding what an agent may read, what it may change, and what happens when one of those steps fails.

I run these systems on my own homelab: ten machines handling routing, monitoring and recovery. I test how these systems fail on that hardware.
