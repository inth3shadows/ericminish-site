Review skills on real code: a three-rep benchmark of Claude Code review setups

By Eric Minish Draft 11 November 2026 18 min read

Status. Draft, version 3. Before publication it is checked by two models from other families, independently, for factual and statistical errors against the data file. Versions 1 and 2 were reviewed this way and changed substantially; see Corrections. Every number on this page is generated from data.json.

Abstract. Skill packs for Claude Code promise better code review, but they are rarely measured on their users' own code. I ran 13 review bundles (bare Claude Code twice, the built-in review command, five public skill packs, my own dual-review skill with and without code-graph tools, and three exploratory hybrids) on 14 review tasks built from real commits in four of my repositories, three times each: 546 reviews. Two blind Claude Opus 5.5 judges adjudicated the findings that matched no planted defect (Cohen's κ 0.884 on the larger round), the accepted defects were listed, and each review was credited only for claims that identify one of them. Dual review found 53.3 real defects per rep against 35.7 for bare Claude Code, a difference of +17.7 (95% interval +10.3 to +25.7), including +7.7 serious (S1–S2) defects per rep (+2.3 to +15.0). Its estimated token cost per review was about 3.3 times bare's and its wall time 4.7 times, and the two dual-review bundles had the lowest precision of those tested. Of the public packs and the built-in command, Superpowers was clearly better than bare Claude Code and Built-in /code-review and ECC were clearly worse. These are comparisons of whole bundles, which differ in models, instructions and compute as well as in skill.

1 Introduction #

Claude Code skills package instructions, agents, hooks and scripts that change how the agent works, and review skills are among the most installed. Their claims are usually supported by examples rather than measurement, and the measurements that exist use other people's code. I wanted to know which review setup to run on my own work.

This paper contributes: (1) a review benchmark built from real commits in the repositories I work in, with planted defects, clean controls and equivalent-mutant traps; (2) a three-rep comparison of 13 bundles, with bare Claude Code run as two independent arms; (3) blind two-judge adjudication of findings, followed by a defect-level attribution step that credits a reviewer only for what it actually said; (4) two-family severity grading of the real defects; and (5) the estimated cost and the time of each bundle.

2 Related work #

SWE-bench and its successors score agents on resolving issues in open-source repositories by whether a test suite passes. METR's study of maintainer review found that many changes passing that grader would not be merged, which is the gap a reviewer is meant to close. Project-level benchmarks such as ProjDevBench fold review compliance into a score. Mutation testing supplies the planted-defect method used here, and its equivalent mutants (changes that alter no behaviour) supply a false-alarm trap. I know of no published comparison of Claude Code review skills on a fixed task set with repeated runs.

3 Method #

3.1 Tasks

Each task is a pull-request-sized change from the history of one of four repositories of mine: a Python market-intelligence pipeline, a Python knowledge-base MCP server, this benchmark's own Python harness, and a Go code-index tool. A task is materialised as a two-commit repository (base and change) with history squashed, so the reviewer cannot read the answer from the log. Of the 14 tasks, 8 carry planted defects (mutations that a test suite shows change behaviour), 4 are clean real commits, and 2 carry an equivalent mutant, which no correct reviewer should flag. Real defects already present in the original commits are counted too.

3.2 Arms

An arm is a whole bundle: skill, agents, hooks and scripts, installed into a fresh sandboxed Claude Code home. The main agent is Claude Opus 5.5 in every arm and Claude Code is pinned to version 2.1.318, but five bundles also start subagents on Claude Sonnet 5.5 (Table 1), so the comparison is between bundles, not skills on a fixed model. Each review runs in a network-restricted sandbox with the same prompt, preceded by a line telling the agent to use the arm's skill (protocol). A guard checked every transcript for the skill or subagent call: every skill arm fired in every review.

3.3 Runs

Round 1 ran rep 0 for the ten arms that existed then (140 reviews). The hybrids were designed after round 1, using round-1 transcripts, so they are exploratory. Round 2 ran reps 1 and 2 for all 13 arms and rep 0 for the hybrids (406 reviews). Claude Code's own estimate of the token cost of all 546 reviews, at API prices, is $256.29; it is an estimate, not what was paid. 207 reviews ran on an API key under a spend limit for the run (some also under a per-review limit of $2.50, Claude Code's --max-budget-usd) and 339 on a subscription token. No review's estimated cost exceeded $1.63, so no limit cut a review short. The credential was set by the run batch, not chosen per arm, but the batches did not balance it across arms (Table A1).

3.4 Scoring

Planted defects. A finding that names a planted defect's location counts as a hit; the rule does not check that the finding describes the planted fault (Section 6).

Adjudication. Findings that match no planted defect are clustered with nearby findings from other arms by file and line, stripped of wording that reveals the arm, and judged blind by two independent Claude Opus 5.5 judges in separate copies of the repository (protocol). Each judge gives one of six verdicts (real and new, real and pre-existing, not a defect, false, not a claim, unverifiable), cites the deciding line, and gives a failing input for a real verdict, running code where it can. A cluster is real only when both judges call it real; clusters they disagree on count as not real. 26 findings that fell next to a dropped plant candidate were neither scored as hits nor adjudicated (Table A1).

Defect attribution. A cluster can hold several different claims, and two clusters can describe one defect. So, per task, a further blind Opus judge listed the distinct defects that both judges' evidence supports (132 defects; 11 supported by one judge only were dropped), then mapped each of the 1632 distinct claims in the task, at any cluster, to one of those defects or to none (921 were mapped; protocol). A review is credited once for each defect it has a mapped claim for. One judge did this step per task.

Severity. Each real cluster was graded S1 (critical) to S4 (trivial) by Claude Opus 5.5 and by a Codex model (Table 6; protocol). Grades one level apart take the more severe; two or more apart take the less severe; a cluster graded by one family takes that grade. A defect takes the most severe grade among its clusters.

Scored and reported lists. The hybrids end with a Confirmed and an Unconfirmed list, and the reader sees both. The main results score the Confirmed list, as designed; Table 4 adds the Unconfirmed list.

Precision is the share of a bundle's claim occurrences in its scored list that map to an accepted defect, with equivalent-mutant flags counted as not real.

3.5 Statistics

The quantity estimated is a bundle's expected yield per review on a task like these 14, including run-to-run variation. Per-rep figures are means over reps, summed over tasks. Intervals are 95% percentile intervals from a two-level bootstrap (10,000 resamples, fixed seed): the same task resamples are used for every arm, and reps are resampled within each task. Differences are paired by task and computed once. Treating the tasks as exchangeable is an assumption: they were chosen by hand and several share a repository. Rep 0 of the ten original arms ran in round 1 under a different adjudication batch, so Table A1 also gives each difference from reps 1–2 alone. The paper reports 29 intervals for differences; at the 95% level about one in twenty would exclude zero by chance even with no real difference, so single borderline results should be read as exploratory.

4 Results #

5 Analysis #

5.1 The two bare arms

Bare (A) and Bare (B) are the same setup. They differ by −4.0 real defects per rep (−8.7 to +0.3). This is one observed comparison, not a calibration of the intervals: it shows a run-to-run gap of this size between identical arms, and differences of similar size elsewhere should be read with that in mind.

5.2 Which bundles differ from bare

Dual review, Dual review + code graph and Superpowers are above bare Claude Code with intervals that exclude zero, and Hybrid: single loop, Built-in /code-review and ECC are below it (Figure 1). Superpowers' difference is +8.0 (+1.7 to +15.3), close to the gap between the two bare arms. Dual review's gain lies in real defects in the original commits (36.7 per rep against 19.3), not in planted ones, which all arms find at similar rates; 3.0 per rep of its defects are pre-existing, outside the change itself.

5.3 Cost, time and precision

Dual review took 210 s and an estimated $0.80 per review, against 45 s and $0.24 for bare. Its precision (0.48) and that of its code-graph variant (0.48) are the lowest of all arms: about half their claims identify no accepted defect. The experiment does not show why the bundle finds more. It uses more compute, two reviewers and a second model, and no matched-compute baseline was run.

5.4 Code-graph tools

Adding code-graph tools changed real defects per rep by −0.3 (−7.7 to +6.3). The interval is wide; the experiment cannot tell a moderate benefit or harm from none.

5.5 Hybrids

Counting their Unconfirmed lists, the hybrids report more real defects than their Confirmed lists alone (Table 4), but none clearly more than dual review: −2.0 (−9.7 to +5.7) for the parallel dual, −3.3 (−11.0 to +5.0) for the pair, and −20.7 (−30.7 to −12.7) for the single loop. The parallel dual uses dual review's two reviewers; its Confirmed list has precision 0.82 against dual review's 0.48, and it moves real defects into the Unconfirmed list. Because the hybrids also change instructions and orchestration, these comparisons do not isolate the verifier.

6 Limitations #

  • Judges from one family. Adjudication and attribution were done by Claude Opus 5.5, grading Claude output, and attribution used one judge per task. No finding was labelled by a person or by a judge from another family.
  • Labels move between rounds. Of 116 round-2 clusters at a spot judged in round 1, 16 got a different real/not-real call. Wording and clustering differ, so this is not a pure test-retest measure, but it is measurement noise the intervals do not include.
  • Severity is soft. The two severity families agree only moderately (linear-weighted κ 0.424 in round 2), and round 1 used a different Codex model, with 26 of its 74 real clusters graded by one family.
  • Coverage. Planted hits are matched by location, not meaning, and 26 findings near dropped plant candidates were not adjudicated.
  • Bundles, not skills. Arms differ in models, subagents, instructions, compute and credential mix; these effects cannot be separated from the bundle comparisons.
  • A small, personal task set. 14 tasks from four repositories I wrote, in Python and Go.
  • The author built one arm and the hybrids. I wrote dual review, and the hybrids were designed with sight of round-1 results; they need held-out tasks before any claim about them generalises.
  • Code is private. The harness and analysis are in private repositories; the protocol files linked above and data.json are public, transcripts are not.

7 Conclusion #

On my code, the dual-review bundle found +17.7 more real defects per rep than bare Claude Code (+10.3 to +25.7), including more serious ones, at about 3.3 times the estimated cost and 4.7 times the time per review, and with the lowest precision of the bundles tested apart from its code-graph variant. Superpowers was also better than bare, by a smaller margin close to the gap between two bare runs; Built-in /code-review and ECC were worse. Code-graph tools and verifier gates did not show a benefit here, though the experiment could not rule one out. Next steps are a replay on real past pull requests, a cross-family or human check of the adjudication, a matched-compute baseline, and held-out tasks for the hybrids.

Corrections #

Version 3 (11 November 2026). The second review (GLM 5.3 Prime and Codex gpt-6.1-sol) found that version 2's attribution judged each claim only against its own cluster's defect, which dropped correct claims about defects accepted at other clusters and merged two different defects in one case; and that precision collapsed several claims from one review into one. Version 3 lists the accepted defects per task and maps every claim to them, measures precision per claim, uses one shared set of resamples so each comparison has a single interval, states the estimand and the exchangeability assumption, labels costs as estimates, reports the reps-1–2-only differences, the findings not adjudicated and the credential imbalance, and publishes the protocol files. Superpowers' difference from bare now excludes zero, and dual review's lead is +17.7.

Version 2. The first review found that every reviewer in a cluster inherited the cluster's verdict, that one root cause could count twice, that the model mix was misstated, that the hybrids' Unconfirmed lists were ignored, and that an ad hoc noise floor was used. Claim-level attribution, two-level resampling and the other fixes lowered dual review's lead over bare from +22.0 to +15.3.
