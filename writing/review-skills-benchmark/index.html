Review skills on real code: a three-rep benchmark of Claude Code review setups

By Eric Minish 11 November 2026 26 min read

Review. Checked independently against the data by two models from other families over five review rounds, and Section 5.6 (economics) over two more; the headline difference moved from +22.0 to +17.7 as attribution was tightened (changelog). Every number on this page is generated from data.json.

Abstract. Skill packs for Claude Code promise better code review, but they are rarely measured on their users' own code. I ran 13 review bundles (bare Claude Code twice, the built-in review command, five public skill packs, my own dual-review skill with and without code-graph tools, and three exploratory hybrids) on 14 review tasks built from real commits in four of my repositories, three times each: 546 reviews. Two blind Claude Opus 5.5 judges adjudicated the findings that matched no planted defect, except 26 next to dropped plant candidates (Cohen's κ 0.884 on the larger round); the planted and accepted defects were then listed per task, and each review was credited once for each listed defect it hit by location or identified in a claim. Dual review found 53.0 real defects per rep against 35.3 for bare Claude Code, a difference of +17.7 (95% interval +10.3 to +26.0), including +6.7 serious (S1–S2) defects per rep (+2.0 to +13.0). Its estimated token cost per review was about 3.3 times that of bare Claude Code and its elapsed time 4.7 times, and the two dual-review bundles had the lowest precision of those tested. Of the public packs and the built-in command, Superpowers scored above bare Claude Code, while Caveman, Ponytail, Built-in /code-review and ECC scored below it, all with 95% intervals that exclude zero; two identical bare arms also differed by −4.7 (−8.7 to −0.7), so differences of that size arise between reruns. These are comparisons of whole bundles, which differ in models, instructions and compute as well as in skill.

1 Introduction #

Claude Code skills package instructions, agents, hooks and scripts that change how the agent works, and review skills are among the most installed. Their claims are usually supported by examples rather than measurement, and the measurements that exist use other people's code. I wanted to know which review setup to run on my own work.

This paper contributes: (1) a review benchmark built from real commits in the repositories I work in, with planted defects, clean controls and equivalent-mutant traps; (2) a three-rep comparison of 13 bundles, with bare Claude Code run as two independent arms; (3) blind two-judge adjudication of findings, followed by a defect-level attribution step that credits a reviewer only for what it said; (4) two-family severity grading of the real defects; and (5) the estimated cost and runtime of each bundle.

2 Related work #

SWE-bench and its successors score agents on resolving issues in open-source repositories by whether a test suite passes. METR's study of maintainer review found that many changes passing that grader would not be merged, which is the gap a reviewer is meant to close. Project-level benchmarks such as ProjDevBench fold review compliance into a score. Mutation testing supplies the planted-defect method used here, and its equivalent mutants (changes that alter no behaviour) supply a false-alarm trap. The closest work is kamui's code-review-bench (github.com/kamui/code-review-bench), which compares Claude Code and Codex review setups, including review skills, on 16 open-source pull requests. Its reference problems are checked by reproduction before and after the change, and it reports detection, claim reliability, clean-change silence and cost separately, with no blended score. When I checked it in November 2026 its scorecard was marked a preview. This paper differs in using my own repositories, planted defects and three reps per arm.

3 Method #

3.1 Tasks

Each task is a pull-request-sized change from the history of one of four repositories of mine: a Python market-intelligence pipeline, a Python knowledge-base MCP server, this benchmark's own Python harness, and a Go code-index tool. A task is materialised as a two-commit repository (base and change) with history squashed, so the reviewer cannot read the answer from the log. Of the 14 tasks, 8 carry planted defects (mutations that a test suite shows change behaviour), 4 are clean real commits, and 2 carry an equivalent mutant, which no correct reviewer should flag. Real defects already present in the original commits are counted too.

3.2 Arms

An arm is a whole bundle: skill, agents, hooks and scripts, installed into a fresh sandboxed Claude Code home. The main agent is Claude Opus 5.5 in every arm and Claude Code is pinned to version 2.1.318, but five bundles also start subagents on Claude Sonnet 5.5 (Table 1), so the comparison is between bundles, not skills on a fixed model. The dual-review and hybrid files are published as run (Appendix), except for one redacted passage in the dual-review skill that describes a private project; the unredacted file is identified by its hash. Each review runs in a network-restricted sandbox with the same prompt, preceded by a line telling the agent to use the arm's skill (protocol). A guard checked every transcript for the skill or subagent call: every skill arm fired in every review.

3.3 Runs

Round 1 ran rep 0 for the ten arms that existed then (140 reviews). The hybrids were designed after round 1, using round-1 transcripts, so they are exploratory. Round 2 ran reps 1 and 2 for all 13 arms and rep 0 for the hybrids (406 reviews). Claude Code's own estimate of the token cost of all 546 reviews, at API prices, is $256.29; it is an estimate, not what was paid. 207 reviews ran on an API key under a batch spend limit ($85 and $13 for the two main key batches, with the 25 reviews of the second also capped at $2.50 per review by Claude Code's --max-budget-usd), and 339 ran on a subscription token. Every attempt that exited non-zero was rerun, whatever it had produced; two such parallel-dual attempts had done work before a usage limit stopped them, and their time and estimated cost ($0.39) are not in the per-review figures. The per-review timeout was 1500 s and the longest review took 1494 s. Launch settings, batches, limits, the rerun rule, file hashes for every arm and the finding-extraction rules are in the run manifest. No review's estimated cost exceeded $1.63, so no limit cut a review short. The credential type (API key or subscription) was set by batch rather than per arm, and the batches did not balance it across arms (Table A1).

3.4 Scoring

Planted defects. A finding that names a planted defect's location counts as a hit; the rule does not check that the finding describes the planted fault (Section 6). A review is also credited with a planted defect when the attribution step below maps one of its claims to it.

Adjudication. Findings that match no planted defect are clustered with nearby findings from other arms by file and line, stripped of wording that reveals the arm, and judged blind by two independent Claude Opus 5.5 judges in separate copies of the repository (protocol). Each judge gives one of six verdicts (REAL_NEW, REAL_OLD for pre-existing, NOT_DEFECT, FALSE, NOT_A_CLAIM, UNVERIFIABLE; no judge used the last), cites the deciding line, and gives a failing input for a REAL_* verdict, running code where it can. A cluster counts as a real defect only when both judges give a REAL_* verdict (REAL_NEW if either says new, otherwise REAL_OLD). When one judge gives a REAL_* verdict and the other does not, the cluster is assigned CONTESTED and not counted as a defect; when neither does and their reasons differ, the first judge's verdict is recorded. 26 findings that fell next to a dropped plant candidate were neither scored as hits nor adjudicated (Table A1).

Defect attribution. A cluster can hold several different claims, and two clusters can describe one defect. So, per task, a further blind Opus judge built a catalogue of defects: every planted defect (36 over both rounds), and each other defect that both judges' evidence supports (103; 9 supported by one judge only were dropped). A real cluster that is a consequence of a planted defect is listed under the plant, so it cannot count twice. The judge marked each defect pre-existing or introduced by the change, then mapped each of the 1632 distinct claims in the task, at any cluster, to every catalogue defect it identifies (928 were mapped to at least one, 31 of them to two or more; protocol). A review is credited once for each catalogue defect it hits by location or identifies in a mapped claim. One judge did this step per task. The catalogue and every mapping are published as attribution.json, with texts given as SHA-256 hashes because the repositories are private.

Severity. Each real cluster was graded S1 (critical) to S4 (trivial) by Claude Opus 5.5 and by a Codex model (Table 6; protocol). Disagreements of one level take the more severe grade; disagreements of two or more levels take the less severe; a cluster graded by only one family takes that grade. A defect takes the most severe grade among its clusters; planted defects are not graded. The graders were told that both judges had reproduced every cluster, but in 39 of the 206 real clusters at least one judge did not report a reproduction. Table 5 therefore also counts serious defects using only clusters that both judges flagged as reproduced. The flag is per cluster: a cluster that supports several defects may not have reproduced each of them, and one cluster's grade can pass to several defects, so this is a sensitivity check, not a count of verified reproductions.

Scored and reported lists. The hybrids end with a Confirmed and an Unconfirmed list, and the reader sees both. The main results score the Confirmed list, as designed; Table 4 adds the Unconfirmed list.

Precision is over a bundle's whole scored list: findings that hit a planted defect plus adjudicated claim occurrences mapped to a catalogue defect, divided by all findings in the list except those near a dropped plant candidate. Equivalent-mutant flags and unmapped claims count against it.

3.5 Statistics

The quantity estimated is a bundle's expected yield per rep, that is per 14 reviews (one per task), on tasks like these. Per-rep figures sum each task's mean across reps. Intervals are 95% percentile intervals from a task-cluster bootstrap (10,000 resamples, fixed seed): each arm's rep-averaged per-task values are resampled by task, with the same task resamples for every arm; reps are not resampled, since resampling them again within tasks double-counts their variance. Differences are paired by task and computed once. Treating the tasks as exchangeable is an assumption: they were chosen by hand and several share a repository. Rep 0 of the ten original arms ran in round 1 under a different adjudication batch, so Table A1 also gives each difference from reps 1–2 alone. The paper reports 31 primary intervals for differences and 24 sensitivity intervals (Tables 5 and A1); at the 95% level about one in twenty would exclude zero by chance even with no true difference, so single borderline results should be read as exploratory.

4 Results #

5 Analysis #

5.1 The two bare arms

Bare (A) and Bare (B) are the same setup. They differ by −4.7 real defects per rep (−8.7 to −0.7), an interval that excludes zero. A correctly calibrated 95% interval excludes zero for two identical arms about one time in twenty, so this one comparison cannot show whether the intervals are too narrow or this is chance. I report it as a negative control, not a threshold: it shows that a gap of this size can arise between identical setups, and differences of similar size below should be read with that in mind.

5.2 Which bundles differ from bare

Dual review + code graph, Dual review and Superpowers are above bare Claude Code, while Caveman, Ponytail, Hybrid: single loop, Built-in /code-review and ECC are below it, all with intervals that exclude zero (Figure 1). Caveman and Ponytail differ from bare by no more than the two bare arms differ from each other. Superpowers' difference is +8.7 (+2.3 to +15.7), about 1.9 times the bare-arm gap, but how far it exceeds that gap is itself uncertain. Dual review's gain lies in real defects in the original commits (36.0 per rep against 19.0), not in planted ones, which all arms find at broadly similar rates (14.7 to 17.3 per rep); 4.0 of its defects per rep are pre-existing, outside the change itself.

5.3 Cost, time and precision

Dual review took 210 s and an estimated $0.80 per review, against 45 s and $0.24 for bare. Its precision (0.61) and that of its code-graph variant (0.59) are the lowest of all arms: about 39% and 41% of their scored findings identify no listed defect. The experiment does not show why the bundle finds more. It uses more compute, two reviewers and a second model, and no matched-compute baseline was run.

5.4 Code-graph tools

Adding code-graph tools changed real defects per rep by +0.3 (−3.7 to +4.3). The interval is wide; the experiment cannot tell a moderate benefit or harm from none.

5.5 Hybrids

Counting their Unconfirmed lists, the hybrids report more real defects than their Confirmed lists alone (Table 4), but none has an interval above dual review's: −1.3 (−6.0 to +3.7) for the parallel dual, −5.0 (−10.3 to +0.7) for the pair, and −21.0 (−31.3 to −12.7) for the single loop. The parallel dual uses dual review's two reviewers; its Confirmed list has precision 0.89 against dual review's 0.61, and it moves real defects into the Unconfirmed list. Because the hybrids also change instructions and orchestration, these comparisons do not isolate the verifier.

5.6 Is it worth it?

A review bundle costs its reader in three ways: the estimated token cost, the time spent reading its findings (true and false), and, for a reader who waits for it, its run time. It repays them in defects caught before they ship. Since there is no reliable figure for what an escaped defect costs (the widely cited phase-escalation multipliers rest on weak evidence; see Bossavit), I do not assume one. Instead, for each step from one bundle to another I compute the break-even: how many minutes of the reader's time a caught defect must be worth for the step to pay. That value is the reader's to judge. It is the expected cost avoided by catching the defect now: the chance it would otherwise ship, times what it would then cost, minus anything catching it early does not save, such as the fix itself. This applies the quality-economics framing of Wagner (ISSTA 2006) to measured per-review differences: break-even = (60 × Δ token cost ÷ hourly value + Δ items to read × triage minutes per item [+ Δ minutes waited]) ÷ Δ defects caught, in minutes. Items to read are everything the reader sees: the whole scored list, including findings next to dropped plants, and the hybrids' Unconfirmed lists. The token cost term uses $100 an hour and barely matters: at $20 an hour it would add 1.1 minutes to dual review's break-even. Triage minutes per item is the reader's to choose; an industrial study of static-analysis alarms puts manual triage at 10 to 20 minutes each (arXiv:2601.18844). No human triage times were measured here, so the 1, 3 and 10 minutes in Table 7 are scenarios for the reader to pick from.

When dual review is worth it. Over bare Claude Code it pays whenever a caught defect is worth more than about 11 minutes of the reader's time at 3 minutes of triage per finding (7 to 18 across the interval), or 4 minutes at 1 minute per finding. Counting only serious (S1–S2) defects, the bar is about 28 minutes. Run time counts only for a reader who waits for the review; one who works on something else meanwhile, such as another session, can count it as near zero. A reader who waits adds about 2 minutes at the benchmark's run times, and each further minute of waiting adds 0.8 minutes to the break-even. Put another way, a defect that would cost an hour if it shipped clears the bar at 3 minutes of triage only if it would ship at least 18% of the time.

When it is not. The break-even grows with triage time: at 10 minutes per item it is about 35 minutes per caught defect. Where findings are slow to check, or where tests and later review would probably catch the defects anyway, the expected cost avoided per defect may not reach that. Most of dual review's cost is its extra items to read (+4.4 per review; of its scored findings, +2.6 more per review identify no defect), not its tokens.

Dual review or Superpowers. Superpowers pays over bare above about 5 minutes per caught defect at 3 minutes of triage, because it adds only +0.9 items to read per review. Going on to dual review adds +0.64 defects per review (95% interval +0.31 to +0.98) for 3.5 more items to read, a break-even of about 16 minutes. Its extra serious defects, +0.14 per review, have an interval that includes zero, so a reader who counts only serious defects and whose triage time is dear has no evidence here that the step from Superpowers to dual review pays.

Bundles below bare. Caveman, Ponytail, Hybrid: single loop, Built-in /code-review and ECC find fewer defects than bare. Ponytail and Hybrid: single loop also give at least as much to read, so switching to them never pays under this model. Caveman, Built-in /code-review and ECC save some reading; switching to one pays only if a caught defect's expected avoided cost is below about 3 minutes at 3 minutes of triage. For a reader whose caught defects are worth more than that, they do not pay as replacements for bare Claude Code.

Run time in everyday use. Of 221 dual-review launches in my own session transcripts (2026-08-20 to 2026-11-11, looking up to two hours after each launch), 200 had a timed code-reviewer report, and I kept the 146 where that half ran 30 seconds or more and its report cited at least one code location. The other 21 launches are left out: 19 had no report within two hours, 1 was overtaken by the next round before its report, and 1 launched no code-reviewer. Dropping late and missing reports under-represents slow rounds, so these are the rounds that could be extracted, not an unrestricted sample. That half alone ran 1 to 61 minutes (median 7.6), far longer than in the benchmark. In the 93 rounds since 2026-09-16, whose reports arrive as a separate message, I split the rounds by the code-reviewer's run time into the 46 shorter and the 47 longer. The longer rounds took a median 11.2 minutes and their reports cited 5 locations, against 4.1 minutes and 3.5 for the shorter ones (Spearman 0.16); in the 53 earlier rounds there was no trend (0.04). The two report formats cite locations at very different rates, so they are not pooled. So longer rounds cited a few more locations and far fewer per minute. This is an association across different reviews: it cannot show what a review would have found if stopped earlier, and longer rounds may be harder changes. For a reader who waits, it suggests a long review costs more per finding; running reviews in the background avoids the wait, though nothing here tests that. Cited locations are only a proxy for findings: they were not adjudicated, and diff size was recorded for only 17 rounds.

These are point estimates of a linear model for one reader and one task set. A fuller treatment would put a distribution on the value of a caught defect and report the probability that each step pays. That is left for the replay on past pull requests.

6 Limitations #

  • Judges from one family. Adjudication and attribution were done by Claude Opus 5.5, grading Claude output, and attribution used one judge per task. No finding was labelled by a person or by a judge from another family.
  • Labels move between rounds. Of 116 round-2 clusters at a spot judged in round 1, 16 got a different call on whether they were a defect. Wording and clustering differ, so this is not a pure test-retest measure, but it is measurement noise the intervals do not include.
  • Severity is soft. The two severity families agree only moderately (linear-weighted κ 0.424 in round 2), and round 1 used a different Codex model, with 26 of its 74 real clusters graded by one family. The graders were also told, wrongly for 39 of 206 clusters, that both judges had reproduced each one (Section 3.4).
  • Blinding was imperfect. In the attribution judges' packets, between 15 and 31 of 1,632 claim texts (a narrow and a broad text scan), most of them from the dual-review arms, still showed that more than one reviewer had written them, through a label such as "(A only)" or "the two reviewers disagree" or two reviewers' views side by side. In one claim the blinding step also cut code (A(B) shown as A). The judges were not asked which arm wrote a claim, and these claims were not re-judged.
  • Coverage. Planted hits are matched by location, not meaning (a mapped claim can also credit a plant), and 26 findings near dropped plant candidates were not adjudicated.
  • Bundles are compared whole. Arms differ in models, subagents, instructions, compute and credential mix; these effects cannot be separated from the bundle comparisons.
  • A small, personal task set. 14 tasks from four repositories I wrote, in Python and Go.
  • I built one arm and the hybrids. I wrote dual review, and designed the hybrids after seeing the round-1 results; they need held-out tasks before any claim about them generalises.
  • Code is private. The harness and analysis are in private repositories; the protocol files, the treatment files for dual review and the hybrids (one passage redacted), the run manifest with every arm's file hashes, attribution.json and data.json are public; transcripts and claim texts are not. The public packs are identified by file hash only, and the number of reviews running at once was not recorded per review.

7 Conclusion #

On my code, the dual-review bundle found +17.7 more real defects per rep than bare Claude Code (+10.3 to +26.0), including more serious ones, at about 3.3 times the estimated cost and 4.7 times the time per review, and with the lowest precision of the bundles tested apart from its code-graph variant. Superpowers also scored above bare Claude Code, by about 1.9 times the gap between the two identical bare arms, while Caveman, Ponytail, Built-in /code-review and ECC scored below it. Code-graph tools did not change yield detectably. The hybrids did not show a yield gain over dual review; the parallel dual's Confirmed list was more precise (0.89 against 0.61) at a lower scored yield, a trade-off these bundle comparisons cannot attribute to the verifier alone. On the break-even analysis (Section 5.6), dual review pays over bare when a caught defect is worth more than about 11 minutes of the reader's time at 3 minutes of triage per finding, and most of its cost is the time spent reading its findings. Next steps are a replay on past pull requests, a cross-family or human check of the adjudication, a matched-compute baseline, and held-out tasks for the hybrids.
