Measuring coding agents by what happens to their code

I compared four Claude models across 681 coding sessions in my own repositories. I could not tell their code survival apart. Their cost per session differed clearly.

By Eric Minish Published 1 November 2026 6 min read

Result. Between 30 June and 1 November 2026, the share of an agent’s code still present later did not differ detectably between Claude Opus 4.8, Opus 5, Opus 5.5 and Sonnet 5. All six pairwise intervals include zero. Cost did differ: on comparable work, Opus 5.5 used about 91,000 more weighted tokens per session than Opus 5 (95% interval 43,000 to 138,000).

Data. 681 coding sessions with checked survival, from 11,611 sessions recorded by flight-recorder. The models were not assigned at random, which is the main limit on these results.

The question #

When I switch the model my coding agent uses, does the code it writes hold up better, and what does the switch cost? Most model comparisons answer this with public benchmarks or with the agent’s own report that a task succeeded. I wanted an answer from my own repositories, using evidence the agent cannot influence: whether its code is still there weeks later.

The data #

Every coding-agent session on my machines leaves a transcript on disk. flight-recorder reads those transcripts after the fact and stores one row per session in SQLite. Between 30 June and 1 November 2026 it recorded 11,611 sessions, 1,297 of them coding sessions, meaning sessions that edited at least one file. 681 of those had lines whose survival could be checked.

Claude Opus 5193

Claude Opus 5.5121

Other models appear in the data with fewer than 20 sessions each and are left out of the comparison.

Cost is measured in weighted tokens: input and output tokens weighted by their relative price, with reads from the prompt cache counted as zero.1 Each session’s cost is reported in thousands of weighted tokens.

How survival is measured #

For each session, flight-recorder hashes every substantive line the agent added. Later, it looks for each hashed line in the current version of the file. A session’s survival is the share of its checked lines that are still present. A survival of 0.85 means 85% of the lines it wrote are still in the code.

Matching on line content matters. Tracking commit IDs instead would score surviving code as deleted whenever history is rebased or squashed, because both operations change every commit ID.

Lines whose file cannot be found are recorded as unknown and left out of the denominator. An early version counted them as deleted, which made one repository score 0.448 when the correct figure was 0.796.

How models are compared #

Comparing all sessions of one model with all sessions of another mixes in the kind of work each one did. A model used mostly in a hard repository looks worse for that reason alone. So sessions are grouped into cohorts: the same repository, the same task type, and a similar change size (small, medium or large).

Within each cohort where both models have at least 4 sessions, the tool takes the difference between their averages. Those differences are then averaged across cohorts. Every figure comes with a 95% interval from a bootstrap over sessions.2 When an interval includes zero, the data does not distinguish the two models on that measure.

Results #

Survival

No pair of models differs detectably in survival. The point estimates are all within 0.08 of zero, and every interval crosses it.

Cost per session

Cost separates the models in five of the six pairs. Opus 5.5 was the most expensive model in every pair it appears in. On comparable work it used about 71,000 more weighted tokens per session than Opus 4.8, 91,000 more than Opus 5, and 138,000 more than Sonnet 5.

Other measures

Sonnet 5 had a higher tool error rate than each Opus model, by 1.3 to 1.8 percentage points. These differences are small, but their intervals exclude zero. Opus 5 read fewer files it never edited, and rewrote less of its own output, than Sonnet 5. The remaining differences in those two measures were inconclusive.

Taken together: on my repositories over these four months, the more expensive models did not produce code that lasted longer. If cost matters, the cheaper models were the better choice on this evidence.

What these results cannot show #

  1. Models were not assigned at random. I chose the model for each session, and my default changed over time. Model, time period and the kind of task I gave each one are mixed together. Cohorts reduce this but cannot remove it.
  2. No detectable difference does not mean no difference. Each model has between 4 and 32 sessions per cohort, and most cohorts have fewer than 15. With intervals this wide, a survival gap of around 10 percentage points between two models could go unseen.
  3. Older sessions have had longer to be rewritten. Survival is checked once, against the current code. A model used mostly in July has had more time for its lines to be replaced than one used in October.
  4. Commits are linked to sessions by time. A session that overlaps a commit I made by hand gets credit for it. This adds noise to interactive sessions.
  5. One developer, one set of repositories. These are my projects and my habits. The method transfers; the numbers do not.

Mistakes in earlier versions #

Each of these produced a confident number that was wrong. They are described in more detail in the flight-recorder case study.

  • The tool error rate read 0.000 everywhere, because about half of failed tool calls are not flagged as errors. It now also checks the text of each result.
  • About 66% of sessions looked like failures, because a later edit to the same file within 7 days counted as rework. Rework is now measured from line survival.
  • One repository scored 0.448 survival instead of 0.796, because unfindable lines counted as deleted.
  • One model looked far worse than another, 0.508 against 0.826, because it had mostly been used in one difficult repository. This is why comparisons are now made within cohorts.

How to reproduce it #

The flight-recorder repository is private, so these commands are for reference. They build the database from local transcripts, score survival against git, and print the comparison above.

python3 ingest.py                  # read new transcripts into SQLite
python3 score.py --git             # link commits, check line survival
python3 report.py models --min-n 4 # matched-pair model comparison

The numbers behind both charts are in data.json, copied from that report on 1 November 2026.
